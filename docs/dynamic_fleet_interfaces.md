# 动态车队及入园、出园接口

任务调度开发需要支持园区车辆数量变化。动态车队记录以 `vehicle_id` 标识车辆，以 `visit_id` 标识一次访问：同车离园后再次注册得到新的访问编号，旧访问的状态、许可和完成事件不能作用于新访问。不把当前 UE 的 24 辆车或测试用 12 车池作为运营车队上限。

参考状态机和接口位于 `src/logistics_park/scheduling/fleet_lifecycle.py`，与 UE、轻量运动学和硬件均无关。

| 接口 | 用途与约束 |
| --- | --- |
| `register_vehicle` | 新车先注册为园外车辆；不能直接参与派单 |
| `request_entry` | 申请指定入口，进入入园等待状态 |
| `authorize_entry` | 接收门口资源预约器签发的许可，校验车辆、访问、入口、方向及时间窗 |
| `confirm_entry` | 后端确认整个车身已进入园区后，进入可派单状态 |
| `adopt_present_vehicle` | 以实际边界观察和当前资源快照接管已有园区车辆，供当前 UE 初始车队使用；不伪造一次入园行驶 |
| `available_vehicle_ids` | 第一版派车算法从这里取候选车，不能直接遍历固定测试车辆列表 |
| `assign_task` / `finish_task` | 占用及归还派车资格；防止同一任务同时分给两辆车 |
| `request_exit` | 立即停止接新单；有当前园区内任务时进入 DRAINING，完成任务后等待出口许可 |
| `authorize_exit` | 获得与当前访问相符的出口时间窗许可后驶向园外 |
| `set_owned_resources` | 汇报实际仍持有的道路容量、路口、共享通道、泊位、等待位及门口预约资源 |
| `confirm_exit` | 必须确认整个车身离开，且同一调度步取得空的资源持有快照；不能在申请离场时提前释放 |
| `DynamicFleetBackend.attach_vehicle` / `detach_vehicle` | 后续由轻量、UE、硬件分别实现注册观测和停止命令/观测；离场不必等同销毁 UE Actor |

新车状态：`OUTSIDE → ENTRY_REQUESTED → ENTERING → IDLE → ON_TASK`。

旧车正常离场：`IDLE → EXIT_REQUESTED → EXITING → DEPARTED`；有当前任务时先 `ON_TASK → DRAINING`，任务完成后再进入 `EXIT_REQUESTED`。只有 IDLE 可接新单，ENTERING 至 EXITING 都仍计入园区车辆。DEPARTED 保留审计记录，不再参与派车。

## 后续接入边界

这是接口和可单测的参考生命周期，不是已经启用的 UE 动态入园/出园系统。具体入口、出口、园外排队点及坐标尚未选择，不假定仓库节点就是园区门口，不修改当前地图。

实际接入时，门口必须成为路网节点，并与道路容量及已有 FIFO/共享资源预约统一：进入许可要同时考虑园区接收容量、门口冲突及下游道路是否可接收；出口许可要考虑门口冲突及园外可接收性。双向共用的出入口应竞争同一物理资源。许可由真实预约器签发，注册表只校验和消费许可，不凭空生成通行权限。

资源持有快照必须由道路、路口、共享通道、泊位和等待区的真实管理器汇总。外部观测确认车尾清空后，先由这些管理器释放资源，再向注册表提交同一调度步的空快照并确认离园。`FleetRegistry` 不自行删除任何物理占用，也不复用测试夹具的“隐藏车辆并清空预约”方法。

入口注册、门口等待、入园、任务分配、离场申请、出口等待和车身完全出园应分别记录，后续可比较接车延迟、在园停留时间和进出吞吐量。后端需在观测/控制中关联访问编号，拒绝旧会话事件。

当前 `AirSimAdapter` 仍采用启动时确定的车辆 ID 集合，`DynamicFleetBackend` 暂为协议。动态挂接/摘除、物理入园/出园及门口联合调度将在任务调度接入阶段实现并实测，不能据本接口宣称 UE 已支持动态增减车。
