# 十字路口滚动预约方案的园区适配

参考材料为用户提供的 `Pasted text.txt`，描述另一个 `/home/aipc/Arrangement_script` 实验。该目录在当前机器不存在，因此尚未检查 `RollingScheduler`、路径生成器或 UE Driver 源码；历史实跑数字仅是材料中的记录，不作为本项目验收证据。

已对照当前实现：`scheduling/fcfs.py` 为路口 FCFS 独占基线，`shared_resource.py` 为车尾清空后释放的窄道 FIFO，`road_capacity.py` 为实际占用和入口承诺数量，`transport_control.py` 负责实际车身、服务、换挡和执行保护。`common/messages.py` 已有 Reservation 和分区时间段的数据契约，项目规划也要求目标抵达时间窗、COMMITTED 约束及局部优化。目前没有参考方案的滚动时间窗或 beam search 实现。

## 借鉴内容及接入层次

| 参考机制 | 当前园区的应用 |
| --- | --- |
| 按转动矩形车身建立局部 Zone | 从已验收轨迹及当前货车包络建立路口冲突单元，不把整段正常道路当作独占区域 |
| 基于预计进入/离开时间预约 | 每个周期更新冲突区预测、时窗及下游容量；释放后保留安全间隔 |
| 从高到低尝试可行速度 | 结合直行、转弯、掉头、倒车及停车约束，减少无必要的低速和停车 |
| 已出发车辆周期性重新优化 | 根据实际进度和当前许可调整后续预测；保护已承诺冲突关系 |
| 有限预算 beam search 与等待公平性 | 优化局部队首顺序，保持同车道 FIFO；对长期等待车辆提升优先级 |
| 出口占用时间窗及半开区间扫描 | 区分未来容量承诺与当前物理占用，减少“前车整段结束后才能放行”的阻塞 |
| 后车及时补位与共享出口跟车 | 结合实际位置与车身间距补位，不能移动到其他车辆已承诺的冲突区域 |
| 同周期快照与独立安全校验 | 车辆统一使用状态快照，再做车身碰撞、跟车、容量和授权检查 |

任务派车、泊位/等待区分配、连续派单仍由园区任务层负责；参考算法用于路口及门口的局部通行与速度优化。两层交换可达时间、排队延迟、目的点容量及资源承诺，不把路口通行评分当成全园区任务分配。

## 当前执行层的适配要求

当前保守货车包络约 8.344 m × 2.60 m，中心偏移 0.75 m；可见车身由多个 OBB 监测。不能使用参考轿车 4.1238 m × 1.9428 m 直接生成冲突区。新增 Zone 要对单元平移和转动膨胀；已包含车身长度的冲突区不能又在时间窗重复加同一车长。

参考实验每周期以恒速预测，并用 `simSetVehiclePose(ignore_collision=True)` 更新位置；这种实验验证的是运动学通行。当前园区 UE 行驶阶段使用真实油门/转向及物理车辆跟踪，位姿设置仅用于试验起止布置。继续保留当前执行和车身安全审计，不改为沿路径瞬移。

预测必须包含实际速度、可达加减速、转弯限速、换挡停稳及 RPC/控制误差。直行目标 8 m/s、转弯 1.5 m/s、掉头与倒车 1 m/s；停车、装卸及最终进位允许零速和合法低速，不能套用整个任务最低速度 1 m/s。调度时钟、UE 加速倍率、观测时钟和实际推进速度需要统一校准；参考 0.5 s 间隔和 0.1 s 周期只作为候选起点，不直接宣称满足当前物理条件或严格实时预算。

当前实际车身还在某区域时，不得仅凭预计离开时间撤销物理占用。预测偏差、错过窗口或退出受阻时必须限制后续放行、重排尚未承诺的预约，并保留必要制动。倒车作业区、窄道和泊位仍按实际车尾清空独占；道路和一般路口才逐步引入局部 Zone 并行。

每个路口的已承诺转向保持不变，清空路口后才能更新后续路径；不将单次实验固定转向规则扩大成车辆整个园区访问永久固定路线。

## 动态车辆及出入口

车辆候选来自 `FleetRegistry`，不依赖参考实验的 8 条进口、每条 3 辆或固定 rank。每个路口按实际同车道位置维护 FIFO，出口汇流顺序按当前承诺维护。

入口及出口同样参与门口冲突区和未来容量预约。入园要考虑接收能力和下游空位，离园要考虑出口及园外可接收性；同车再次入园以 `visit_id` 隔离旧许可。离场申请立即停止接新单，资源释放仍由实际车尾清空与真实资源管理器确认。具体门口点位尚未配置，实际动态 UE 后端还未实现。

## 后续实施顺序

1. 先接入任务层基础调度：动态车队、预计到达时间派车、泊位及等待区分配、连续任务；通行阶段暂复用现有 FCFS 和共享资源基线，让任务调度真正驱动车辆。
2. 建立独立冲突区/时间窗管理器，验证停在区内、刚释放的安全间隔、未来容量和超窗等边界；继续复用现有路由、货车控制和实际车身审计。
3. 在管理器上接入候选速度、局部顺序搜索、公平性和补位；优化结果提交前统一校验已承诺预约。
4. 用少量针对性多车任务比较基线与滚动调度，记录完成数、排队时间、停车次数、吞吐量、碰撞及容量违规；再做 UE 物理闭环。

复用已完成的 25 条去重实车扫图证据，新增算法验证针对实际调度组合，不重新逐跑 132 条。当前文件只是适配计划，没有更换运行中的调度算法，没有修改地图或启动 UE 控制程序。

## 当前实施状态更新

任务层和双车连续闭环已接通，24 车 UE 基线压力测试暴露全队停滞。现已实现并接入可选 `RollingResourceReservations`：近邻区域联合申请、实测出口门控、预测占用时长与等待老化排序；任务层保护已下发路线，诊断器记录等待依赖循环。预测窗口只用于估计/排序，实际租约必须车尾清空后释放。这是滚动放行原型，完整未来出口容量、候选速度搜索及 beam search 尚未实现。

原型的 24 车轻量测试仍未通过，尚未运行优化版 UE。后续优先解决装卸容量循环和过大的独占区域，不继续扩大路网枚举测试。结果和范围见[24 车与优化状态](ue_fleet24_scheduler_status.md)。
